# 코퍼스 스키마

이 문서는 `systems/`, `patterns/`, `tokens/` 아래 문서들이 지켜야 할 고정 형식을 정의합니다.
**100개가 서로 비교 가능해지려면 형식이 고정돼야 합니다.** 새 항목을 추가할 때 이 문서를 먼저 읽으세요.

## 원칙

1. **사실 우선.** 토큰 실값, 스케일, 컴포넌트 목록, 치수처럼 검증 가능한 정보를 최우선으로 담습니다.
   "아름답다", "직관적이다" 같은 평가어는 넣지 않습니다.
2. **원문 복사 금지.** 가이드라인 산문은 요약·재서술하고 출처를 링크합니다.
   토큰 값·스케일 같은 사실 정보는 그대로 인용해도 무방합니다.
3. **추측 금지 — 값과 이유 모두에 적용됩니다.**

   확인하지 못한 값은 비워두고 `미확인`으로 표시합니다.
   그럴듯한 값을 채워넣으면 코퍼스 전체의 신뢰도가 무너집니다.

   **더 자주 어기게 되는 쪽은 "왜"입니다.** 관찰한 사실에 그럴듯한 이유를 붙이고 싶어지는데,
   출처에 적혀 있지 않으면 그건 지어낸 것입니다. 관찰만 적고 이유는 생략하세요.

   | 쓰지 말 것 | 쓸 것 |
   |------------|-------|
   | 하단 터치 타겟이 48pt인데, 엄지 도달 영역이라 키운 것으로 보입니다 | 상단 44pt, 하단 48pt. 킷에 이유는 적혀 있지 않습니다 |
   | 라운드가 큰 건 카드 중심 UI를 반영한 것으로 보입니다 | 라운드 최대가 32px입니다 |
   | 접근성 요구를 스케일에 반영한 것으로 보입니다 | 44px 단계가 있습니다. 소스에 근거는 적혀 있지 않습니다 |

   금지 표현: `~로 보입니다` · `~것으로 추정됩니다` · `~때문입니다` · `~의도로` ·
   `~자연스러운 선택입니다` · `~효과를 노린` — 출처에 명시된 경우가 아니면 쓰지 않습니다.

   **비교·대조는 추측이 아닙니다.** "Ant Design은 14px, Canvas는 16px"처럼 관찰끼리
   나란히 놓는 것은 사실 진술입니다. 거기에 "왜 그런지"를 붙이는 순간 추측이 됩니다.

   출처가 이유를 명시한 경우에는 **명시했다는 사실과 함께** 적습니다.
   예: "소스 주석은 반응형 맵을 우선 쓰라고 명시합니다."
4. **검증일 필수.** 디자인시스템은 계속 바뀝니다. `verified` 날짜 없는 항목은 신뢰할 수 없습니다.

## 수집 깊이 (`coverage`)

**이 코퍼스가 그 시스템을 어디까지 담았는지**를 나타냅니다. 시스템의 품질·성숙도·
중요도 순위가 **아닙니다.**

| 값 | 담긴 깊이 | 분량 | 추가 요구사항 |
|----|-----------|------|--------------|
| `full` | 컴포넌트 수준까지 — 변형·상태·치수 | 250~400줄 | `## 컴포넌트 상세` 표 |
| `partial` | 토큰까지. 컴포넌트는 목록만 | 100~200줄 | — |
| `minimal` | 문서층 메모 수준 | ~60줄 | — |
| `internal` | 자체 제품 표본. **공개 데이터에서 제외** | — | `build-data.mjs`가 걸러냅니다 |

> **예전엔 `tier: A | B | C`였습니다.** 서열(등급)로 읽히는 이름이라 바꿨습니다 —
> 각국 정부 디자인시스템처럼 **상대 평가로 오해되면 곤란한 항목**이 포함돼 있고,
> 실제로 A/B를 가른 조건도 품질이 아니라 **우리가 수집할 수 있었던 범위**였습니다.
> 상류가 컴포넌트 치수까지 공개했으면 `full`이 되고, 토큰까지만 공개했으면
> `partial`이 됩니다. 즉 이 값은 **상류의 공개 범위 × 우리 수집량**이지
> 그 시스템이 좋은지 나쁜지가 아닙니다.

## 언어 판본

문서는 **영어를 주 노출본**으로 두고 한국어 원문을 나란히 보존합니다.

| 파일 | 언어 | 성격 |
|------|------|------|
| `<slug>.md` | 영어 | **주 노출본.** 생성기·사이트·에이전트가 읽는 판본 |
| `<slug>.ko.md` | 한국어 | 저자가 조사하며 실제로 쓴 원문 |

- 접미사가 **없는** 쪽이 영어인 이유: 루트 `README.md`(영어) + `README.ko.md`가
  이미 같은 규약이고, 사이트·에이전트 소비가 영어 기준입니다. 코퍼스 문서만
  반대로 두면 규약이 둘로 갈립니다.
- 각 판본 머리에 **언어 전환 링크**가 들어갑니다. 손으로 쓰지 말고
  `node design-systems/i18n.mjs --links`로 생성하세요.
- 생성기는 **접미사 없는 판본만** 읽습니다. 그러지 않으면 같은 시스템이 언어
  수만큼 중복 집계됩니다(`build-data.mjs`의 `LANG_SUFFIX`).
- 언어를 늘리려면 `<slug>.ja.md` 처럼 두고 `i18n.mjs`의 `LANG_NAME`에 이름만
  추가하면 됩니다.

**이주는 문서 단위로 진행 중입니다.** 아직 옮기지 않은 문서는 `<slug>.md`에
한국어인 채로 남아 있고 생성기가 그대로 읽습니다 — 그래서 이주 도중에도 사이트가
깨지지 않습니다. 검증은 `node design-systems/i18n.mjs --check` (CI에 걸려 있음).

## `systems/<slug>.md`

슬러그는 소문자 케밥케이스, 제품명 기준입니다 (`carbon`, `material-3`, `apple-hig`).
회사명이 아닌 시스템명을 씁니다 — IBM이 아니라 Carbon.

### Frontmatter (전 항목 필수)

```yaml
---
name: Carbon Design System     # 공식 표기 그대로
org: IBM
coverage: full                 # full | partial | minimal | internal
url: https://carbondesignsystem.com
repo: https://github.com/carbon-design-system/carbon   # 없으면 null
license: Apache-2.0            # 문서/코드 라이선스, 다르면 "code: X, docs: Y"
tech: [React, Web Components, Angular, Vue]            # 공식 제공 구현체만
figma_kit: true                # 공식 Figma 라이브러리 제공 여부
tokens_format: [JSON, SCSS, CSS]   # 토큰 배포 형식, 없으면 []
a11y_target: WCAG 2.1 AA       # 명시된 목표, 없으면 null
platform: web                  # web | mobile | desktop | spatial | wearable | tv | automotive
                               # 여러 플랫폼이면 배열: [web, mobile]
domain: enterprise             # enterprise | consumer | commerce | os | public | health | data |
                               # framework | aerospace
verified: 2026-08-16           # 이 문서를 실제로 확인한 날짜
---
```

`domain`은 `patterns/` 교차 정리에서 "엔터프라이즈는 이렇게, 커머스는 이렇게" 식으로
묶을 때 씁니다. 값이 애매하면 주 사용처 기준으로 하나만 고릅니다.

**`framework`는 사용자층이 없는 경우입니다.** Tailwind CSS · shadcn/ui · Mantine ·
Radix Themes처럼 **회사 제품이 아니라 다른 사람이 제품을 만들 때 쓰는 도구**입니다.
사용자층으로 분류할 수 없어 추가한 값입니다.

**`aerospace`는 외부 규격이 토큰을 정하는 경우입니다.** Astro UXDS(우주 관제)가
보안 등급 색 6종(`unclassified` ~ `topsecretsci`)을 토큰으로 두는데,
이건 디자인 판단이 아니라 미국 정부 문서 분류 규격입니다.
차량 플랫폼의 24sp 최소 폰트와 같은 종류의 제약입니다 (`platforms.md`).

이 구분은 실제로 결론을 갈랐습니다 — 스페이싱 공통 코어 `4/8/16/24`의
유일한 반례(Mantine)가 `framework` 도메인에서 나왔습니다 (`tokens/scales.md`).

**도메인 값을 새로 만들 때 기준:** 기존 값으로 담으면 **그 시스템이 왜 그렇게
결정했는지가 사라지는 경우**에만 추가합니다. Astro UXDS를 `enterprise`로 넣으면
등급색이 그냥 특이한 팔레트로 보이고, 관제라는 맥락이 지워집니다.
**도메인별로 나눠 보지 않으면 "표본 하나가 뚫었다"는 사실만 남고
그것이 어떤 종류의 시스템이었는지가 사라집니다.**

**`platform`과 `domain`을 혼동하지 마세요.** `platform`은 실행 환경,
`domain`은 사용자층입니다. Material 3은 `platform: [web, mobile]`이면서 `domain: os`입니다.

플랫폼이 다르면 토큰 구조 자체가 다릅니다 — 웹 시스템은 전부 스페이싱을 토큰화하는데
모바일 OS는 전부 안 합니다. 자세한 근거는 `platforms.md`를 보세요.

### 본문 섹션 (순서 고정)

빈 섹션은 삭제하지 말고 `미확인`으로 남깁니다 — 누락인지 아직 안 본 건지 구분돼야 합니다.

```markdown
## 한 줄 요약
무엇을 위한 시스템인지 한 문장. 여기서 성격이 안 드러나면 아래를 읽을 이유가 없습니다.

## 토큰
### 스페이싱
실제 스케일 값을 나열하고 base를 밝힙니다. 예: `2/4/8/12/16/24/32/40/48 (base 8)`
### 타이포그래피
크기 스케일 + 서체. 라인하이트 규칙이 있으면 함께.
### 컬러
팔레트 구성 방식 (단계 수, 시맨틱 레이어 유무). 전체 헥스값 나열은 하지 않습니다 — 원문 링크로 갈음.
### 라운드 / 엘리베이션
반경 스케일과 그림자 단계.

## 컴포넌트
제공 컴포넌트 목록. 개수를 함께 적습니다.

## 특징적 결정
★ 이 코퍼스의 핵심 섹션입니다.
다른 시스템과 갈리는 지점과 그 근거를 적습니다. 예: "라운드 0을 고수 — 산업용 톤".
"버튼이 있다" 같은 공통 사실은 여기 쓰지 않습니다. 차이만 씁니다.

## 접근성
명시된 준수 목표, 자체 검증 도구, 특별히 신경 쓴 영역.

## 참고
원문 링크 목록. 토큰 파일 직링크가 있으면 특히 유용합니다.
```

### `full` 수집 시 추가 섹션

`## 특징적 결정` 뒤에 넣습니다.

```markdown
## 컴포넌트 상세
### Button
| 변형 | 용도 | 높이 |
|------|------|------|
| primary | 화면당 1개 주요 액션 | 48px |

상태: default / hover / focus / active / disabled / loading
포커스링: 2px inset + 1px outset

### Modal
(동일 형식)
```

최소 다음 컴포넌트는 다룹니다: Button, Modal/Dialog, Form(Input/Select), Table, Navigation.
`patterns/`가 이 다섯 축으로 교차 정리되기 때문입니다.

## `patterns/<component>.md`

컴포넌트 하나를 여러 시스템에 걸쳐 비교합니다. **UI 만들 때 실제로 펴보는 문서**입니다.

```markdown
# Modal

## <결정 축 1>
| 시스템 | <옵션A> | <옵션B> |
|--------|---------|---------|

→ 수렴/분기 지점을 한두 줄로. 표만 있고 해석이 없으면 쓸모가 반감됩니다.

## <결정 축 2>
...

## 구현 시 기본값
합의된 지점을 실행 가능한 기본값으로 정리. 이 섹션이 이 문서의 목적입니다.
```

축은 **실제로 갈리는 결정**으로 잡습니다. 모두가 똑같이 하는 것은 축이 될 수 없습니다.
모달이라면 닫기 수단, 너비 단계, 포커스 트랩, 모바일 전환 방식 등입니다.

## `tokens/scales.md`

스페이싱·타이포·라운드 스케일을 시스템 간 비교합니다. 형식은 `patterns/`와 동일합니다.

## 검증 규칙

- frontmatter의 `url`은 실제로 열어보고 적습니다. 링크가 죽으면 항목 전체를 의심해야 합니다.
- `license`는 저장소의 LICENSE 파일 기준입니다. 문서와 코드 라이선스가 다른 경우가 흔합니다.
- 토큰 실값은 공식 문서나 토큰 파일에서 확인한 것만 적습니다. 예제 코드에서 역추론하지 않습니다.
