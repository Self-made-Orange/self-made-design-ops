# 디자인 검수 지침 — 코퍼스를 근거로 정확하게

시안(Figma)이나 구현(코드)을 **`design-systems/` 코퍼스를 근거로 검수**할 때의
절차입니다. 목적은 "예쁘다/이상하다"가 아니라 **"표본 대비 어디에 서 있고,
이탈이라면 의도인지 실수인지"**를 가려내는 것입니다.

> **(2026-08-18 실전 검증 반영)** 이 지침은 정착 플래너 대시보드에 처음 실제로
> 돌아갔습니다 — 결과는 `agents/case-studies/frr-dashboard-review.md`.
> 그때 막혔던 자리를 아래 "(2026-08-18 실전 검증 반영)" 표기 항목으로 고쳤습니다.

> **(2026-08-18 실전 검증 반영)** 이전 판은 "104개 표본 대비"라고 본문에 숫자를
> 박아 뒀는데, 코퍼스가 자라면 바로 낡습니다. **표본 수는 여기 적지 않습니다.**
> 축마다 표본 수가 다르므로(재종합 시점 기준 68~83) **각 `patterns/*.md` 상단에서
> 그 축의 표본 수를 읽어 리포트에 옮겨 적으세요.** 전체 규모는 `design-systems/index.md`.

## 검수의 3판정

모든 지적은 셋 중 하나로 분류합니다. 이 분류가 없는 지적은 내지 않습니다.

| 판정 | 뜻 | 예 |
|------|-----|-----|
| **수렴 이탈** | 표본 다수가 합의한 값에서 벗어남 — 이유를 물어야 함 | 터치 타겟 32px (Apple 44pt·Material 48dp 미달) |
| **허용 분기** | 표본 자체가 갈리는 축 — 이탈이 아니라 선택 | 본문 14px (CJK 관행) vs 16px (서구 웹 관행) |
| **내부 비일관** | 외부 표본과 무관하게 시안 안에서 어긋남 | 버튼은 8px 격자인데 카드 패딩만 10px |

**가장 가치 있는 지적은 세 번째입니다.** 코퍼스 없이도 찾을 수 있지만,
코퍼스가 있으면 "이 값이 실수인지 의도인지"를 물을 기준이 생깁니다.

### 내부 비일관의 하위 유형 — 계약 불일치 (2026-08-18 실전 검증 반영)

대상이 **하나가 아닐 때**가 흔합니다 — 디자인시스템 카탈로그 + 실제 구현,
Figma 라이브러리 + 코드, 디자인 토큰 파일 + 컴포넌트. 이때 **둘 사이의 어긋남도
내부 비일관**이며, 보통 나머지 비일관의 상위 원인입니다.

- 검수 시작 전에 **어느 것이 계약이고 어느 것이 구현인지** 정하세요.
- 계약 불일치는 개별 항목으로 흩지 말고 **한 항목으로 묶어** 원인을 적습니다
  ("토큰 선언이 두 벌이라 드리프트가 구조적으로 보장됨" 같은 형태).
- 계약 쪽이 틀린 경우가 실제로 나옵니다. 어느 쪽이 맞는지 근거로 판정하세요.

## 절차

### 0. 대상의 좌표를 먼저 잡습니다

`design-systems/platforms.md`의 축으로 대상을 분류합니다 —
플랫폼(모바일/데스크톱/TV/워치/차량), 시청 거리, 입력 방식(터치/포인터/리모컨/크라운·베젤).
**플랫폼이 다르면 기준 수치가 통째로 다릅니다** (TV는 포커스 간격, 워치는 안전 영역).
웹/모바일 앱이 아니면 반드시 이 파일부터 읽으세요.

**한 대상이 두 축에 걸치는 경우를 먼저 확인하세요** (2026-08-18 실전 검증 반영) —
반응형 웹은 데스크톱 브레이크포인트에서 포인터, 모바일 브레이크포인트에서 터치입니다.
**터치 타겟·서체 크기는 모바일 브레이크포인트에서만 판정**하고, 판정 자리를 리포트에 적습니다.

### 0-a. 대상의 리비전을 고정합니다 (2026-08-18 실전 검증 반영)

리포트 서두에 **커밋 해시 / 파일 버전 / 시안 버전**을 적습니다.
코퍼스 쪽 `verified` 날짜를 보라고 하면서 대상 쪽을 안 적으면 리포트가 재현 불가입니다.

### 0-b. 코퍼스에 이 대상의 표본이 이미 있는지 확인합니다 (2026-08-18 실전 검증 반영)

```bash
ls design-systems/systems/ | grep -i <대상>
```

**있으면 그것이 최우선 근거입니다.** 외부 표본 대조보다 먼저 읽으세요 —
토큰 구조·파생 관계·이미 알려진 불일치·"남은 확인 사항"이 적혀 있어
같은 것을 다시 찾느라 시간을 쓰지 않게 됩니다.

**그리고 표본과 대상 리비전이 다르면 표본이 틀렸을 수 있습니다.**
실측이 표본과 어긋나면 리포트에 **"코퍼스 표본 정정"** 절을 따로 두고 적으세요.
표본 갱신 자체는 검수의 범위가 아니지만, 기록을 남기지 않으면 다음 사람이 같은 함정에 빠집니다.

### 0-c. 대상에 `DESIGN.md`가 있으면 린터를 먼저 돌립니다 (2026-08-18 조사 반영)

제품 루트에 `DESIGN.md`(에이전트용 시각 정체성 파일)가 있으면 **사람이 보기 전에
기계 검사를 통과시킵니다.**

```bash
npx @google/design.md lint DESIGN.md    # JSON 출력, 오류 시 exit 1
```

린터가 잡는 것: 대비비(WCAG 자동 계산) · 깨진 토큰 참조 · 고아 토큰 ·
섹션 순서 · 미지 키 · 중복 제목. **이걸 손으로 확인하지 마세요.**

**단 "린트 통과 = 완성"이 아닙니다** — 빈 `colors`는 잡히지 않는 것으로
관측됐습니다(`design-systems/INTEROP.md`). 린터가 통과시킨 뒤에도
3판정 검수는 그대로 수행합니다. 또 이 포맷에는 **모션·밀도·플랫폼 분기·
터치 타겟 자리가 없으므로**, 그 축들은 코퍼스 문서로 검수해야 합니다.

### 1. 축별 점검 — 여는 파일과 기준

**대상에 없는 축은 건너뜁니다** (2026-08-18 실전 검증 반영). 아래 표는 체크리스트가
아니라 색인입니다. 모달이 없는 제품에서 모달 축을 "미확인"으로 채우지 마세요 —
**적용 대상 없음**은 "확인 못 한 것"에 한 줄로 적고 넘어갑니다.

**각 문서를 열 때는 "N표본 재종합" 절을 먼저 보세요** (2026-08-18 실전 검증 반영).
`button` · `form` · `modal` · `motion` · `color` · `typography` · `table` 7축에는
2026-08-18 재종합 절이 있고, **문서 앞부분의 결론과 어긋나면 재종합 절이 우선입니다**
(각 문서 상단에 그렇게 적혀 있습니다). 아래 표의 "핵심 기준"도 재종합 이후 값입니다.

**재종합 절이 없는 축은 표본 기반이 다릅니다** (2026-08-18 실전 검증 반영) —
`tokens/scales.md`는 스페이싱 스케일 확인분(60여 개) 위에 서 있으나 "구현 시 기본값"
절은 24표본 기준 권고이고, `navigation.md`·`feedback.md`는 재종합 대상이 아니었습니다.
**리포트에는 그 축의 실제 표본 수를 적으세요.** 코퍼스 전체 규모를 축의 표본 수인 양 쓰지 않습니다.

### 1-a. 대비는 계산합니다 (2026-08-18 실전 검증 반영)

"눈대중 금지"라고만 적혀 있고 계산 방법이 없어 실전에서 막혔던 자리입니다.
**WCAG 상대휘도 식으로 직접 계산하세요.** 색을 나열만 하고 넘어가지 않습니다.

```python
def lin(c):
    c = c / 255
    return c/12.92 if c <= 0.03928 else ((c+0.055)/1.055)**2.4
def L(hex):
    h = hex.lstrip('#'); r,g,b = (int(h[i:i+2],16) for i in (0,2,4))
    return 0.2126*lin(r) + 0.7152*lin(g) + 0.0722*lin(b)
def ratio(fg, bg):
    a, b = sorted((L(fg), L(bg)), reverse=True)
    return round((a+0.05)/(b+0.05), 2)
```

- **배경을 실제 배경으로 넣으세요.** 같은 글자색이 흰 배경에서 통과하고
  `surface-2`/`bg`에서 떨어지는 일이 흔합니다 — 토큰 조합별로 돌려야 드러납니다.
- **large text 예외를 함부로 적용하지 마세요** — 18.66px 볼드 또는 24px 이상입니다.
  배지·캡션(11~13px)은 어떤 굵기여도 4.5:1이 기준입니다.
- **차트는 3:1(WCAG 1.4.11)에 더해 계열 상호 대비도 봅니다.** 배경 대비를 통과해도
  계열끼리 구분이 안 되면 색만으로 데이터를 가른 것입니다.
- 상태색(hover·active)도 함께 계산하세요. **정지 상태만 미달인 경우**가 나옵니다.

### 2. Figma 시안일 때

> **시안이 아니면 이 절을 건너뜁니다.** (2026-08-18 실전 검증 반영)

- MCP로 실값을 읽습니다 (`get_design_context` · `get_variable_defs`).
  스크린샷 눈대중으로 수치를 판정하지 않습니다 — **수치는 반드시 실측**.
- 변수(토큰)로 정의됐는지, 리터럴인지를 구분해서 봅니다.
  값이 맞아도 리터럴 난립이면 유지보수 지적 대상입니다.
- 컴포넌트의 상태 variant(hover·disabled 등)가 시안에 존재하는지 확인합니다 —
  구현자가 임의로 채우게 되는 공백이 가장 흔한 품질 저하 지점입니다.

### 3. 코드일 때

- 토큰/변수 정의 파일부터 찾고, 컴포넌트가 그걸 참조하는지 리터럴을 박는지 봅니다.
  **정의 파일이 여러 벌이면 그 자체를 먼저 적으세요** (2026-08-18 실전 검증 반영) —
  빌드 없는 정적 HTML 여러 장이 각자 `:root`를 선언하는 형태가 실제로 나옵니다.
- 스페이싱·색·라운드의 **리터럴 출현 빈도**를 grep으로 세면 내부 비일관이
  기계적으로 드러납니다.

  ```bash
  grep -oE 'border-radius: ?[0-9]+px' f.html | grep -oE '[0-9]+px' | sort -n | uniq -c | sort -rn
  grep -oiE '#[0-9a-f]{6}\b' f.html | tr 'A-Z' 'a-z' | sort | uniq -c | sort -rn
  ```

  **헥스 빈도표에서 "거의 같은 값"을 찾으세요** (2026-08-18 실전 검증 반영) —
  토큰과 한두 자리만 다른 색이 스크립트·차트 팔레트에 따로 사는 경우가 있습니다.
  육안으로는 절대 안 잡히고 빈도표에서만 보입니다.
- 접근성 훅: `:focus-visible` 유무, `aria-invalid`/`disabled` 처리,
  `prefers-reduced-motion`, 논리 속성(`margin-inline-*`) 사용 여부.

### 3-a. 렌더 실측 — 가능하면 하고, 안 되면 그렇게 적습니다 (2026-08-18 실전 검증 반영)

**CSS 선언만 읽으면 파생 높이를 놓칩니다.** `font: inherit` + 패딩만 있는 버튼이
루트 16px을 물려받아 형제보다 크게 뜨는 식입니다. 정적 HTML이면 헤드리스로 실측하세요.

```bash
# 페이지 사본에 측정 스크립트를 주입하고 DOM을 덤프
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --no-sandbox --user-data-dir=/tmp/probe \
  --window-size=1440,900 --virtual-time-budget=5000 \
  --dump-dom "file://$PWD/copy.html"
```

측정할 것: `getBoundingClientRect().height` 히스토그램(같은 위계 컨트롤이 몇 단인지),
`getComputedStyle`의 `fontSize`·`fontWeight`·`borderRadius`·`color`·`backgroundColor`.
**모바일 브레이크포인트에서 한 번 더 돌리세요** — 헤드리스 최소 창 폭 제약이 있으면
실제로 측정한 폭을 리포트에 적습니다.

**끝나면 반드시 프로세스를 정리하세요 (2026-08-18 실전 검증 반영).**
`--virtual-time-budget`을 줘도 헤드리스 인스턴스가 GPU 헬퍼를 물고 남는 경우가
있습니다 — 실제로 첫 실전 적용에서 **17개가 좀비로 남아 약 1.5GB를 잡고
있었습니다**(CPU는 0%). 프로필 디렉터리를 프로브 전용 이름으로 두고, 그것으로
골라 죽이세요 — 사용자가 쓰는 일반 브라우저를 건드리면 안 됩니다.

```bash
# 프로브 전용 프로필만 골라 종료 (일반 Chrome은 건드리지 않음)
PIDS=$(ps aux | grep "[G]oogle Chrome" | grep "cdp-probe" | awk '{print $2}')
kill $PIDS; sleep 2
kill -9 $(ps aux | grep "[G]oogle Chrome" | grep "cdp-probe" | awk '{print $2}') 2>/dev/null
rm -rf /tmp/cdp-probe*
```

`kill`(TERM)에 안 죽는 경우가 있으므로 **잔존 확인 후 `-9`까지** 준비하세요.

**렌더 실측이 불가능할 때**(인증 게이트·API 의존·런타임 생성 DOM):

- **선언 실측 + 박스모델 파생**까지가 허용 근거입니다. 리포트에서 파생값에 `파생`을 표기하세요.
- **"실측했다"고 쓰지 않습니다.** 파생값은 렌더 결과와 다를 수 있습니다.
- 사본에만 스크립트를 주입하고 **대상 저장소는 읽기 전용으로 다룹니다.**

## 리포트 형식

```markdown
## 검수 리포트 — <대상> (<날짜>)

| 항목 | 값 |
|------|-----|
| 대상 리비전 | <커밋/버전> |
| 좌표 | <플랫폼·입력 방식·판정 브레이크포인트> |
| 기존 코퍼스 표본 | <systems/*.md 또는 없음> |
| 실측 방법 | <렌더 실측 / 선언 실측+파생 / MCP 실값> |

### 판정 요약
| 판정 | 건수 |
|------|:---:|
| 수렴 이탈 | N |
| 허용 분기 | N |
| 내부 비일관 | N |

### <판정별로 묶어서>

| # | 항목 | 관찰값 | 코퍼스 근거 (표본 수) | 권고 |
|---|------|--------|----------------------|------|
| E1 | 버튼 높이 | 34px | `button.md` 77표본 재종합 — 분포 28~56, 최빈 40 | 32 또는 36 |

### 판정하지 않은 것
- … (표본 수를 댈 수 없는 축 등)

### 질문 (판정 불가 항목)
- …

### 확인 못 한 것
- … (미확인 사유)

### 코퍼스 표본 정정 (표본이 있었던 경우)
- …
```

- **판정별로 묶습니다** (2026-08-18 실전 검증 반영). 한 표에 섞으면 "이탈이 몇 건인지"가
  안 보입니다. 서두의 판정 요약 표는 필수입니다.
- **근거 열에 표본 수를 함께 적습니다** (2026-08-18 실전 검증 반영). `agents/README.md`의
  공통 규율("표본 수를 함께 말합니다")을 지킬 자리가 이전 판 표에는 없었습니다.
- **판정 불가면 질문으로 넘깁니다.** 억지로 판정하지 않습니다.
- 심각도 순서: 접근성(포커스·대비·타겟) → 내부 비일관 → 수렴 이탈 → 취향.
  **취향은 리포트에 넣지 않습니다.**
- 개수를 채우려 하지 않습니다 — 지적 0건이면 "코퍼스 기준 특이점 없음"이 결론입니다.

### 산출물을 어디에 두는가 (2026-08-18 실전 검증 반영)

`agents/README.md` 공통 규율 3(제품 데이터 반입 금지)과 충돌하기 쉬운 자리입니다.

- **리포트 본체는 해당 제품 저장소로 보냅니다.**
- **코퍼스에 남기는 것은 절차 검증 기록뿐**이며 `agents/case-studies/`에 둡니다.
  이때 인용은 **판정의 근거가 된 값만** — 토큰 표·전체 팔레트·문자열을 옮기지 않습니다.
- 이미 `design-systems/systems/`에 내부 표본이 있는 제품이면, 표본 정정 사항은
  리포트에 적고 표본 파일 갱신은 별도 작업으로 넘깁니다.

## 코퍼스가 스스로 어긋나 있을 때 (2026-08-18 실전 검증 반영)

실제로 나옵니다 — 같은 절의 제목·표·본문이 다른 표본 수를 말하는 식.

- **임의로 한쪽을 고르지 않습니다.** 리포트의 "부수 발견"에 어긋난 자리를 그대로 적고,
  그 값에 의존하는 판정은 보류하거나 표본 수를 명시한 채 약하게 냅니다.
- 문서 앞부분과 재종합 절이 다르면 **재종합 절이 우선**입니다(이건 규칙이 있습니다).
- **재종합 절 안에서도 표와 요약 문장이 갈립니다 — 표가 기준입니다** (2026-08-19 정정
  반영). `typography.md`의 14px 진영이 표에서는 17표본인데 200줄 아래 "구현 시 기본값"
  요약은 13개로 남아 있던 사례가 실제로 있었습니다. **보강분은 표에 들어가고 요약
  문장은 손대지 않은 채 남는 경로**가 반복 확인됐습니다. 숫자를 인용하기 전에
  그 축의 표를 한 번 세어 보세요.

## 금지

- 코퍼스에 없는 수치를 "업계 표준"이라며 인용하는 것 (근거 파일 없으면 미확인)
- 스크린샷 눈대중 수치 판정
- 계산하지 않은 대비 판정 (2026-08-18 실전 검증 반영)
- 선언에서 파생한 값을 "실측"이라고 쓰는 것 (2026-08-18 실전 검증 반영)
- 허용 분기를 위반처럼 쓰는 것 ("16px이 표준인데 14px을 쓰고 있음" — 틀린 지적)
- 재종합 절을 안 읽고 문서 앞부분의 낡은 결론을 인용하는 것 (2026-08-18 실전 검증 반영)
- 검수 중에 대상 저장소를 수정하는 것 — 사본에서 작업합니다 (2026-08-18 실전 검증 반영)
