# 자체 검증 — `localization.md` × `i18n/` (2026-08-18)

> **이것은 `agents/localization.md` 절차의 첫 적용 기록입니다.**
> `design-review.md`와 달리 이 지침은 "대상 제품이 없다"는 이유로 미검증이었습니다
> (`TODO.md` D절). 대상 제품 대신 **코퍼스 자체 자산**(`i18n/`)에 절차를 돌렸습니다.
>
> **아래 인용된 린터 출력이 한국어인 것은 당시 도구가 그렇게 찍었기 때문입니다.**

> `node lint.mjs … --lang=ko`로 그대로 재현됩니다 (`tools/cli-i18n.mjs`).

## 이 기록의 한계 — 먼저 읽으세요

**대상이 제품이 아니라 코퍼스 자체 자산이므로, 절차의 기계적 정합성은 검증되지만
제품 맥락 판단은 검증되지 않습니다.**

| 검증됨 | 검증되지 않음 |
|--------|---------------|
| 지침이 지시하는 명령이 실제로 실행되는가 | 번역의 품질·자연스러움 (네이티브 검수 축) |
| 지침의 요구 산출물이 도구·포맷에 자리가 있는가 | 용어집 확정 과정 (사용자 확인 루프) |

| 린터가 규약 위반을 실제로 잡는가 | Figma 텍스트 노드 수집 (대상 파일 없음) |
| 인용한 코퍼스 근거가 실재하는가 | RTL 실제 구현 전환 (코드 대상 없음) |

Figma 파일도 없습니다. 절차 2~5는 `ko-KR.json`·`en-US.json`·`kr.json`을
**제출된 산출물로 간주**해 적용했습니다.

## 2단계 — 절차 자체의 결함

### L1. §5의 명령이 실행되지 않습니다

```bash
node i18n/lint.mjs ko-KR.json --against en-US.json   # ENOENT
```

스크립트만 `i18n/` 접두사를 받고 데이터 파일은 못 받았습니다. `i18n/README.md`는
디렉터리 안에서 실행하는 형태(`node lint.mjs …`)로 일관돼 있어 문제가 없고,
**지침이 루트 기준으로 옮겨 적으면서 절반만 고친 것**입니다.
`event-instrumentation.md` §6은 같은 함정을 피했습니다(입력이 사용자 파일이라 접두사가 필요 없음).

### L2. `--strict` 없이는 위반 12건에도 exit 0입니다

`lint.mjs:300` — `return strict && total ? 1 : 0`.
지침 §5도 `i18n/README.md`의 검사 스크립트 절도 **`--strict`와 `--against`를 함께 쓴
예시를 한 번도 보여주지 않습니다.** README의 세 예시는 `단일 파일` · `--against` ·
`*.json --strict`이고, 마지막 것은 `--against`가 없어 **번역 누락·플레이스홀더 일치·
길이 예산 검사가 통째로 빠집니다.**

**`event-taxonomy/convert.mjs --lint-only`는 반대로 `--strict` 없이도 exit 1입니다**
(`convert.mjs:368`). 두 도구의 종료 코드 관례가 반대인데 어느 지침도 이를 적지 않습니다.
에이전트나 CI가 종료 코드로 판정하면 i18n 쪽이 조용히 통과합니다.

실무에서 필요한 조합은 다음 하나이고, 이것이 어디에도 적혀 있지 않습니다.

```bash
node lint.mjs ko-KR.json --against en-US.json --strict
```

### L3. §3 맥락 메타데이터에 템플릿도 검사도 실물도 없습니다

지침은 §3에서 메타데이터 파일을 만들라 하고 §5 산출물 목록에도 넣습니다. 그런데

- 코퍼스에 메타데이터 파일이 **0개**입니다 (`template.json`은 문자열 템플릿)
- `lint.mjs`에 메타데이터를 읽는 경로가 없습니다 — `maxLength`가 선언돼도 검사되지 않습니다
- **`doNotTranslate`의 위치가 두 문서에서 다릅니다.** 지침 §3은 키별 배열
  (`"chart.legend.cycle": { "doNotTranslate": ["Acme"] }`), `i18n/README.md`의
  "번역하지 않는 것" 절은 "파일에 `doNotTranslate` 목록을 두고 관리합니다"(파일 단위 목록)

이 결함은 다음 관찰과 맞물립니다: `en-US.json`은 `common.action.close`와
`common.state.closed`가 **둘 다 `"Close"`** 입니다. `i18n/README.md`가
"영어로는 둘 다 Close에 가깝지만"이라고 밝힌 **의도된 표본**이므로 결함이 아닙니다.
그러나 **린터는 기준 파일 내부의 동일 값 중복을 검사하지 않으며**, 영어 파일만 받은
번역자는 두 키를 구분할 수단이 없습니다 — 메타데이터 파일이 실물로 없으면
지침 §3이 막으려던 오역이 그대로 발생합니다.

### L4. §4의 CJK 축소 리스크를 도구가 전혀 재지 않습니다

지침 §4는 "CJK ↔ 서구 언어: 길이가 양방향으로 다릅니다 … 기준 언어 하나로 레이아웃을
잡았는지를 리스크로 보고합니다"라고 요구합니다. `expansionBudget`(`lint.mjs:44-50`)은
**상한만** 정의하고, 검사도 `ratio > budget` 한 방향뿐입니다(`lint.mjs:216`).

실측에서 `home.cta.primary` 36% · `common.action.close` 40%가 README의 50~70% 밴드
아래인데 린터는 위반 0건을 냅니다. **§5의 리스크 리포트에 "길이 초과 위험 키"만 적혀
있고 축소 항목이 없는 것도 같은 누락입니다.**

### L5. §4의 typography.md 인용이 2026-08-18 재종합으로 낡았습니다

지침 §4는 `design-systems/patterns/typography.md`를 **"(14px CJK / 16px 서구 웹 / 17pt iOS)"**
로 요약해 인용합니다. 해당 문서의 현재 상태는 다릅니다.

| 지침의 요약 | `patterns/typography.md` 실제 |
|-------------|------------------------------|
| 3분류 | **"본문 기본 크기 — 6개 진영으로 갈립니다"** (13·14·16·17·18·24) |
| 17pt = iOS | 17행: "**Apple iOS**(Body) · **KRDS**(body.medium) · **디지털청**(日)" · 36~37행: "**셋 다 CJK 문맥입니다**" |
| 16px = 서구 웹 | 16px 진영에 **Charcoal(pixiv) · Serendie(三菱電機, expanded) · SmartHR(M)** — 일본 표본 3종 |
| — | 5행: "컴포넌트 층까지 서체 실측이 확보된 시스템은 **68개**입니다 (2026-08-18 재종합)" · 7~8행 "**둘이 어긋나면 재종합 절이 우선**" |

`i18n/README.md`의 "본문 글자 크기 — 코퍼스에서 확인된 사실" 표도 같은 3분류를
싣고 있어 **동일한 낡음이 규약 문서에도 있습니다**(이 리포트의 범위 밖이라 기록만 남깁니다).

`agents/design-review.md`는 같은 문제로 개정돼 "각 `patterns/*.md` 상단에서 그 축의
표본 수를 읽어" · "재종합 절이 우선입니다"를 넣었습니다. **`localization.md`에는
그 개정이 반영되지 않았습니다.**

### L6. Radix Themes 논리 속성 근거가 코퍼스에 없습니다

§4 RTL 절: "코퍼스 표본: shadcn/ui가 `--font-ar`·`--font-he` 언어별 서체 토큰을 두고,
**Mantine·Radix Themes가 논리 속성을 씁니다.**"

| 주장 | 확인 |
|------|------|
| shadcn/ui `--font-ar`·`--font-he` | **✓** `patterns/typography.md:464`, `:491-492` |
| Mantine 논리 속성 | **✓** `patterns/button.md:230`(`border-end-end-radius`) · `patterns/form.md:235`(`inset-inline-start` 트랜지션) |
| **Radix Themes 논리 속성** | **✗ 근거 없음** — `systems/radix-themes.md`에 `inline-start`·`inline-end`·`논리 속성`·`RTL` 0건. 코퍼스 전체에서 `Radix`와 `inline`이 같은 줄에 등장하는 사례 0건 |

코퍼스의 논리 속성 표본은 Mantine 외에 **Cloudscape**("얼럿 치수" 절,
`patterns/feedback.md:126-132`의 `border-width-alert-inline-start` 토큰)가 있습니다.
근거 파일을 적지 않은 것 자체가
`agents/README.md` 공통 규율 2(인용 의무: 파일과 절을 적습니다) 위반입니다.

### L7. 코퍼스의 빈 템플릿이 코퍼스의 CI 예시를 깨뜨립니다

`parseLocale`(`lint.mjs:59-84`)이 파일명 전체를 로케일로 읽으므로 `template.json`이
"언어 코드가 2~3자가 아닙니다"로 걸립니다. README가 `template.json`을 "빈 템플릿"으로
등재하고 동시에 `node lint.mjs *.json --strict`를 CI 예시로 제시하므로,
**규약대로 하면 CI가 첫날부터 빨간불입니다.**

### L8. `common.*` 네임스페이스가 §2 스키마에 없습니다

§2는 `<화면>.<요소>.<용도>`, "흔한 오판" 표는 "한 키를 여러 화면에서 재사용 → 맥락
다르면 분리"입니다. 그런데 코퍼스 예시의 `common.action.close`는 **의도적으로
화면 횡단**이고 린터도 통과시킵니다. 화면 횡단 네임스페이스를 언제 허용하는지
지침에 규칙이 없어 **즉흥 판단이 필요했습니다.**

### L9. 키 세그먼트 수가 규약 3단 / 린터 2단으로 어긋납니다

`KEY_RE`(`lint.mjs:134`)는 점 구분 세그먼트 **2개 이상**을 통과시킵니다.
`home.item_count`·`checkout.total`(2단)이 위반 0건입니다. 규약은 3단(`<화면>.<요소>.<용도>`)
이므로, 3단을 강제할 것인지 2단을 허용할 것인지 문서에 결론이 없습니다.

### L10. §4 어미 통일에 고정 인사말·구두점 규칙이 없습니다

`ko-KR.json`의 톤을 §4대로 "관찰"하면 다음이 나옵니다.

| 값 | 형태 |
|----|------|
| 시작하기 · 닫기 · 마감됨 | 명사형 |
| {userName}님 안녕하세요 | 해요체, 마침표 **없음** |
| 카드가 거절되었습니다. | 합쇼체, 마침표 **있음** |

문장 2건의 어미 등급과 구두점이 갈립니다. 다만 "안녕하세요"는 **고정 인사말**이라
어미 통일 대상으로 볼지가 판단 사안이고, **지침에 고정 인사말·관용구 처리와 구두점
정책이 없어 즉흥 판단이 필요했습니다.** 린터에도 톤·구두점 검사는 없습니다(설계상 타당).

## 위반 0건으로 끝난 항목

억지로 문제를 만들지 않기 위해 적습니다.

- **`ko-KR.json` 린트 — 위반 0건.** 키 명명·ICU 문법·복수형 카테고리·플레이스홀더
  일치·길이 예산·번역 누락·미번역 잔존 전부 통과
- **조사 삽입 (§4)** — 0건. `{userName}님`·`{#}개 항목` 모두 변수 뒤 조사를 피함
- **`close`/`closed` 분리 (§2)** — 규약대로 키가 나뉘고 한국어에서 실제로 다른 단어
- **ICU 숫자·통화** — `::currency/KRW` 사용, 문자열 포맷 박기 0건
- **비영어 기준 경고** — 지침이 예고한 동작·거짓 양성이 그대로 재현
- **아랍어 CLDR 6카테고리 검사** — probe에서 정상 동작 확인
