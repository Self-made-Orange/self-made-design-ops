# 참조 시스템 선정 지침 — 제품에 맞는 표본 고르기

새 제품·기능을 시작할 때 **"어떤 공개 디자인시스템을 참조로 삼을지"를
코퍼스 근거로 정하는** 절차입니다. 이 저장소의 초기 목표("참조하는 것만으로
UI 제작에 도움")의 정문에 해당하는 지침이며, 소비자 세션의 실전 수행
(`case-studies/system-selection-calendar.md`)에서 검증된 행동을 절차로
추출한 것입니다.

## 원칙

1. **단일 채택이 아니라 축별 분할이 기본입니다.** 제품이 여러 좌표(플랫폼·
   거리·문화권·도메인)에 걸치면 좌표마다 최적 표본이 다릅니다 — 한 시스템을
   통째로 채택하라는 결론은 제품이 좌표 하나에만 있을 때나 성립합니다.
2. **사용자 선호는 출발점이지 결론이 아닙니다.** "Apple·Toss를 기본으로"
   같은 지정이 있으면 그것을 기본 진영으로 놓고, **축이 갈리는 곳에서만**
   다른 표본을 얹습니다. 선호를 뒤집을 때는 근거(표본 수)를 요구하세요.
3. **"시스템"과 "제품 문법"을 구분합니다.** 경쟁 제품 스크린샷(예: 특정
   제품의 화면)은 디자인시스템이 아닙니다 — 거기서 가져오는 것은 값이 아니라
   **문법**(구성원 색 배정, 현재 시각 표시 같은 관례)이고, 그렇게 표기합니다.
4. **라이선스 게이트를 통과해야 채택 방식이 정해집니다.** frontmatter
   `license`를 확인하고 — 미확인이면 **값·구조만 참조, 코드 이식 금지**를
   명시합니다. 사실 데이터(수치)는 라이선스와 무관하게 참조 가능합니다.
5. **버리는 것도 결정입니다.** 참조에서 무엇을 *안* 가져오는지(예: 흰 배경
   고정을 버림)를 근거와 함께 적어야 다음 사람이 재론하지 않습니다.

## 절차

### 1. 제품 좌표 잡기 — `platforms.md`의 축으로

| 축 | 물을 것 |
|----|---------|
| 플랫폼 | web / mobile / desktop / spatial / automotive / wearable / tv 중 어디? **복수면 축별 분할 확정** |
| 시청 거리 | 20cm(워치)~3m(TV) — 같은 앱이 두 거리를 커버하면 거리별로 참조가 갈립니다 |
| 입력 | 터치 / 포인터 / 리모컨 / 크라운·베젤 |
| 밀도 전제 | 소비자 여백형 vs 엔터프라이즈 밀집형 |

### 2. 좌표마다 표본 찾기

- `data/systems.json`의 frontmatter(platform · domain · org)로 필터 →
  해당 `systems/*.md`만 읽습니다
- 좌표에 표본이 몇 개인지 밝히세요 — "3m 표본은 TV 계열 2개뿐" 같은
  **표본 수 진술**이 선정의 신뢰도입니다
- 표본이 0인 좌표는 그렇게 적습니다 (미확인 규율 — 그럴듯한 대체 표본을
  표본인 척 세우지 않습니다)

### 3. 언어·문화권 축

한국어/일본어/중국어 제품이면 해당 문화권 표본을 타이포 축에 얹습니다 —
본문 크기·자간 관행이 문자 문화권마다 다르다는 코퍼스 결론
(`patterns/typography.md`) 때문에 이 축은 생략하면 틀립니다.

### 4. 도메인 유사 표본

`domain` 필드로 유사 도메인(commerce · health · transit · government …)
표본을 찾아 **판단 지침**(패턴 관례)을 보강합니다. 값은 플랫폼 축에서,
관례는 도메인 축에서 오는 경우가 많습니다.

### 5. 라이선스 게이트

선정된 각 표본에 대해 채택 방식을 표로 확정합니다:

| 방식 | 조건 |
|------|------|
| 코드 이식 | 라이선스 명시(MIT·Apache 등)이고 호환될 때만 |
| 구조·값 참조 | 라이선스 미확인이어도 가능 (수치는 사실 데이터) |
| 문법 참조 | 경쟁 제품·스크린샷 — 항상 이것뿐 |

### 6. 산출물 — 제품 저장소에 리서치 문서

`docs/research/design-systems.md` 형태를 권합니다. 필수 요소:

- **축 | 참조 | 핵심 근거** 표 — 근거에 표본 수 포함
- 각 참조에서 **가져올 실용 자산**(토큰·산식·기법)과 **버리는 것** 명시
- 기존 플랜/작업 항목과의 연결 (어느 작업이 어느 참조를 소비하는지)
- 라이선스 표기 (미확인 표본의 "값만 참조" 명시 포함)

산출물은 **제품 저장소에** 커밋합니다 — 이 저장소에는 커밋하지 않습니다.

### 6-1. 선정 결과를 `DESIGN.md`로 굳히기 (선택)

제품이 코딩 에이전트에게 시각 정체성을 넘기는 구조라면, 리서치 문서와 별개로
**`DESIGN.md`**(에이전트용 교환 포맷)를 함께 두면 적용이 확실해집니다.

```bash
node self-made-design-ops/design-systems/to-design-md.mjs --name "<제품>" -o DESIGN.md
npx @google/design.md lint DESIGN.md      # 대비비·깨진 참조·섹션 순서 검사
```

스캐폴드는 코퍼스의 "구현 시 기본값"에서 나오므로, **선정한 참조에서 가져오기로
한 값으로 덮어쓰는 것이 본 작업**입니다. 포맷 상세·주의(모션 자리 없음, 빈 색을
린터가 안 잡음)는 `design-systems/INTEROP.md`.

## 흔한 오판 (하지 말 것)

| 오판 | 바른 처리 |
|------|-----------|
| "제일 유명한 것 하나 채택" | 축별 분할 + 표본 수 근거 |
| 경쟁 제품 스크린샷을 시스템처럼 인용 | "제품 문법" 표기로 분리 |
| 라이선스 미확인 표본의 코드 이식 | 값·구조 참조로 제한 |
| 표본 없는 좌표에 그럴듯한 대체 표본 | "표본 없음"으로 적고 실물 검증 계획 |
| 사용자 선호를 무근거로 뒤집기 | 뒤집으려면 표본 근거 제시 |
| 선정만 하고 반영 지점 없음 | 플랜 작업 항목과 표로 연결 |
