# 이벤트 시트 제안 지침 — UX 맥락에서 이벤트를 도출합니다

Figma 파일이나 코드에서 **UX 맥락(화면·경로·행동)을 읽고**,
`event-taxonomy/` 규약에 맞는 이벤트 시트를 **제안**하는 절차입니다.

전제: `event-taxonomy/README.md`를 먼저 읽으세요. 이 문서는 그 규약을
반복하지 않고, **맥락을 읽어 시트를 채우는 방법**만 다룹니다.

> **(2026-08-18 자체 검증 반영)** 이 지침을 코퍼스 자체 자산(`event-taxonomy/`)에
> 돌렸습니다 — 결과는 `agents/case-studies/event-taxonomy-selfcheck.md`.
> 막혔던 자리를 아래 "(2026-08-18 자체 검증 반영)" 표기 항목으로 고쳤습니다.
> **제품 맥락 판단(화면 인벤토리·카테고리 도출·enum 정규화)은 대상이 없어
> 여전히 미검증입니다** — 절차 1~2를 처음 제품에 돌릴 때 다시 기록하세요.

## 원칙

1. **이벤트는 질문에서 나옵니다.** "이 화면에 버튼이 있으니 이벤트를 단다"가
   아니라 "무엇을 알고 싶은가"가 먼저입니다. 제안하는 모든 이벤트에
   **측정 목적 한 줄**을 붙입니다. 목적을 못 쓰는 이벤트는 제안하지 않습니다.

   **측정 목적은 CSV 밖 별도 목록에 적습니다** (2026-08-18 자체 검증 반영).
   이전 판은 "비고 컬럼 또는 별도 목록"이라고 했는데, **비고 컬럼은 쓸 수 없습니다** —
   `convert.mjs`는 비고가 정확히 `필수`일 때만 그 표기를 걷어내므로
   (`필수` 문자열 전체 일치, `convert.mjs:92`), `필수 · 목적: …`으로 적으면
   `필수`가 조건 컬럼에 그대로 남아 md·html·Notion 전 타깃에 출력됩니다.
   **8번째 컬럼을 새로 만드는 것도 안 됩니다** — 컬럼이 7개로 고정돼 있어
   (`convert.mjs:19`) 린터는 통과시키고 변환기는 조용히 버립니다.

   ```
   이벤트 목적 목록 (시트와 함께 제출)
   onboarding_view  — 단계별 이탈 지점 특정
   checkout_click   — 결제수단 선택 분포와 쿠폰 사용률
   ```
2. **비즈니스 의미를 창작하지 않습니다.** 화면에서 읽을 수 없는 것
   (전환 목표, 핵심 지표, 요금제 구분)은 **질문 목록**으로 사용자에게 넘깁니다.
3. **PII를 프로퍼티로 제안하지 않습니다.** 이름·이메일·전화번호·정확한 위치·
   건강 수치 원값은 금지. 필요하면 파생값(구간·불리언)으로 대체 제안합니다.
4. **제안일 뿐입니다.** 미확정 enum은 규약대로 `…`를 남깁니다.

   **"초안 — 검토 필요" 표시는 CSV가 아니라 전달 문서에 답니다**
   (2026-08-18 자체 검증 반영). CSV에 초안 컬럼이 없고 `convert.mjs`의 md·html
   렌더러도 초안 상태를 출력하지 않으므로, 시트 안에 적으면 변환 뒤 사라집니다.
   **목적 목록·질문 목록·커버리지 선언을 담는 전달 문서 서두에 답니다**
   (§6의 산출물 묶음).

## 절차

### 1. 화면 인벤토리

**Figma에서:** `get_metadata`로 페이지·최상위 프레임을 열거합니다.
프레임 이름이 곧 화면 후보지만, 그대로 믿지 않습니다 —
같은 화면의 상태 변형(에러/빈/로딩)이 별도 프레임으로 그려져 있는 게 보통입니다.
**상태 변형은 화면이 아니라 프로퍼티 후보입니다** (`state: error | empty | loading`).

**코드에서:** 라우트 정의(라우터 설정, 파일 기반 라우팅 디렉터리)가 화면 목록입니다.
모달·바텀시트는 라우트가 아니어도 **사용자가 "진입"으로 인식하면 view 대상**입니다
(전체 화면을 덮고 체류가 발생하는 것 기준). 툴팁·토스트는 view가 아닙니다.

### 2. 카테고리 도출 (3~6개)

화면 인벤토리를 기능 영역으로 묶습니다. 내비게이션 구조(탭바·사이드바 항목)가
1차 후보입니다. 화면 수가 아니라 **도메인이 기준**입니다 — 규약의
"화면마다 이벤트를 만들지 않습니다" 원칙이 여기서 결정됩니다.

### 3. 이벤트 뼈대 — 카테고리 × {`_view`, `_click`}

각 카테고리에 `_view`/`_click` 두 개로 시작하고, 화면·버튼은
`screen_name`/`button_name` enum으로 넣습니다.

- **enum 값 정규화:** Figma 프레임 이름 "3-2. 기기 연결 완료 ✅"를 그대로 쓰지
  않습니다 → `device_connected`. 소문자 스네이크케이스, 번호·이모지·조사 제거,
  코드가 있으면 라우트명과 일치시킵니다.
- `_view`/`_click`으로 안 되는 동작(제출·완료·취소 같은 결과 이벤트)만
  추가하고, 추가하면 그 이유를 적습니다. **이유도 비고 컬럼이 아니라 목적 목록에
  적습니다** (2026-08-18 자체 검증 반영 — 원칙 1과 같은 이유).
  `example.csv`의 `search_submit`이 이유 없이 추가된 상태이고 **린터는 이를
  잡지 못합니다.** 예시를 근거로 삼지 마세요.

### 4. 퍼널을 명시합니다

온보딩·결제·핵심 과업처럼 **순서가 있는 경로**를 화면 흐름(Figma 프로토타입
연결, 코드의 네비게이션 호출)에서 식별하고, 시트와 별도로 퍼널 절을 둡니다:

```
가입 퍼널: sdk_view(scan_qr) → sdk_view(device_found) → sdk_view(analyzing) → sdk_view(done)
이탈 관측: 각 단계 view 수 비교로 측정 (별도 이벤트 불필요)
```

**퍼널 단계는 같은 이벤트의 enum 값 순서로 표현합니다** — 규약의 핵심 이점이
퍼널 분석이므로, 단계를 다른 이벤트로 쪼개자는 제안은 하지 않습니다.

**퍼널 절은 전달 문서에 둡니다** (2026-08-18 자체 검증 반영). CSV 컬럼에도
`convert.mjs`에도 퍼널 개념이 없어 시트에 적을 자리가 없습니다 — 위 코드블록
형식 그대로 전달 문서에 넣으세요. **순서가 있는 경로인데 퍼널 절이 없으면
누락입니다** (`example.csv`의 온보딩이 `welcome → permission → profile → complete` +
`step_index`로 명백한 퍼널인데 퍼널 절이 없는 상태입니다).

### 5. 프로퍼티와 조건

- 화면 안의 **분기 상태**(신규/기존, 성공/실패, 개수)를 프로퍼티 후보로 잡습니다.
- 조건부 프로퍼티는 **언제 붙는지**를 조건 컬럼에 반드시 적습니다.
- 값 목록을 화면에서 다 읽을 수 없으면 `값1 | 값2 | …`로 미확정 표시합니다.

### 6. 검증하고 넘깁니다

```bash
node event-taxonomy/convert.mjs 초안.csv --lint-only
```

**종료 코드 계약** (2026-08-18 자체 검증 반영) — `--lint-only`는 `--strict` 없이도
위반이 있으면 **exit 1**입니다 (`convert.mjs:368`). `i18n/lint.mjs`는 반대로
`--strict` 없이는 위반이 있어도 exit 0이므로, **두 도구를 같은 CI 스크립트에
넣을 때 관례가 다르다는 것을 알고 쓰세요** (`agents/localization.md` §5).

**`…` 하나만 남은 위반은 통과로 봅니다** (2026-08-18 자체 검증 반영).
원칙 4는 미확정 enum에 `…`를 남기라 하고 린터는 그것을 위반으로 셉니다 —
**두 요구를 동시에 만족하는 시트는 존재하지 않습니다.** `…`는 위반이 아니라
**잔여 작업 알림**입니다. 처리 방법:

- `…` 항목은 **질문 목록으로 올리고** 시트에는 그대로 둡니다
- 넘기기 전 확인해야 할 것은 **`…` 외의 위반이 0건인가**입니다
- `--strict`를 CI에 걸 때는 `…`가 게이트를 막는다는 점을 팀에 알리거나,
  확정 시점 전까지 `--strict`를 쓰지 않습니다
- 코퍼스의 `example.csv`도 이 이유로 위반 2건이 뜹니다 — **예시는 통과 기준이
  아닙니다**

**린터가 잡지 않는 것은 눈으로 확인합니다** (2026-08-18 자체 검증 반영).
규약의 검토 항목 중 아래는 구현돼 있지 않습니다.

| 규약 항목 | 린터 | 사람이 확인할 것 |
|-----------|:----:|------------------|
| 화면 위치 (컬럼 표에서 **필수**) | ✗ | 공란인 채로 통과합니다 |
| 화면 단위로 이벤트를 쪼개지 않았는가 | ✗ | §3 원칙을 직접 대조 |
| 카테고리 ↔ 접두사 **일치** | △ | 같은 카테고리에 다른 도메인이 섞인 경우만 검출. `온보딩`/`onboarding`처럼 표기가 달라도 통과하고, **두 카테고리가 한 이벤트명을 공유해도 통과**합니다 |
| 제품 고유 데이터 혼입 | ✗ | 공통 규율 3 |

**같은 이벤트명을 다른 카테고리에서 쓰지 마세요** — 규약 위반일 뿐 아니라,
뒤 행의 화면 위치가 비어 있으면 `normalize`가 앞 이벤트에 병합해
**카테고리·트리거를 경고 없이 버립니다** (`convert.mjs:69-84`).
변환 후 이벤트 수가 예상과 맞는지 확인하세요.

통과한 CSV + 아래 목록을 **전달 문서 한 벌로** 함께 냅니다
(서두에 "초안 — 검토 필요", 원칙 4):

- **목적 목록** — 이벤트별 측정 목적 한 줄 (원칙 1)
- **퍼널 절** — 순서 있는 경로 (§4)
- **질문 목록** — 판단 못 한 것 (이 모달은 view인가, 이 지표가 필요한가…)
  + `…`로 남은 미확정 enum
- **커버리지 선언** — 어떤 화면/영역을 시트에 담지 않았고 왜인지
  (예: 설정 화면은 요청 범위 밖). 침묵으로 빠뜨리지 않습니다.

## 흔한 오판 (하지 말 것)

| 오판 | 바른 처리 |
|------|-----------|
| 프레임마다 `_view` 이벤트 생성 | 화면은 `screen_name` enum |
| 에러 화면을 `screen_name`에 추가 | 같은 화면의 상태면 `state`/`error_code` 프로퍼티 |
| 버튼마다 이벤트 생성 | `button_name` enum |
| 뒤로가기·닫기 무시 | 퍼널 이탈 관측에 필요하면 `button_name: back \| close`로 포함 |
| "나중에 쓸지 모르니" 프로퍼티 추가 | 측정 목적 없으면 제안하지 않음 |
| Figma에 없는 화면을 상상으로 보완 | 질문 목록으로 |
